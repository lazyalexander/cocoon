# Offline agent-project experiment

English (authoritative) · [简体中文](PROJECT.zh-CN.md)

[User guide](../../docs/user-guide.md) · [Persistence experiment](PERSISTENCE.md)

This explicit trusted-operator experiment uses a real macOS VM, an independent
ext4 disk, a Rust Linux helper and virtio-vsock. No SSH, network device, shared
host directory, GPU or native execution fallback is configured. It is a fixed
acceptance workflow, not a public agent API or complete Debian development image.

## Run

Use the prerequisites and pinned kernel acquisition in the [user guide](../../docs/user-guide.md).
The project option additionally downloads the pinned Debian kernel package for
its vsock modules. Existing files with a mismatched digest are refused.

```sh
python3 experiments/microvm/root_modules.py --project
python3 experiments/microvm/probe.py build
cargo build --release --locked -p cocoon
python3 experiments/microvm/build_root.py --project
python3 experiments/microvm/project.py --fixture /absolute/private/root-BUILD_ID --kernel /absolute/private/linux --rounds 3
```

Use the private directory printed by `build_root.py`. Real VM execution requires
the macOS virtualization entitlement and an execution context that permits it.
The harness creates a new private state directory, imports the image, registers
one VM and calls the Rust supervisor for each boot. The equivalent fixed command
for an already registered VM with the project fixture is:

```text
cocoon host ABSOLUTE_PRIVATE_STATE_DIR experiment project VM_UUID ABSOLUTE_SIGNED_RUNNER
```

`vm start` remains unavailable. Do not pass a persistence-only fixture to the
project experiment. Downloads and generated images/reports stay ignored locally.
The full kernel package is build input only; the image contains selected modules.

## What is exercised

Eight sequential requests cross vsock in each boot:

1. Import a knowledge file into `/workspace/knowledge.txt`.
2. Import an intentionally unfinished shell script.
3. Read the script back and check its exact bytes.
4. Replace it with code that reads the knowledge file and produces an artifact.
5. Execute `/bin/sh build.sh` in `/workspace`; require exit 0 and `TEST_PASS`.
6. Read the artifact bytes back.
7. Verify a separate command's stderr and exit code 7.
8. Verify the helper's two-second command timeout.

The host validates every response identity and expected value. Only after the
framework confirms stopping does it receive the verified content into a new
`artifact.txt` under that boot's private directory, with mode 0600, size and
SHA-256 in the report. Guest filenames never select host destinations; existing
files are not overwritten, and returned content is never executed on the host.
The harness checks artifact bytes and hash, the stored stopped state, and the
unchanged baseline disk. This demonstrates a headless shell-code workflow;
it does not test model reasoning or a third-party agent integration.

## Bounds and authority

`cocoon-guest-wire` owns the strict typed schema and four-byte big-endian length
framing; `cocoon-guest-helper` owns Linux execution and vsock. Host control crates
still forbid unsafe code. The helper has no registration, image, grant, reclaim
or host-path operation. Caller attribution, task UUID, boot/attempt identity and
request sequence are separate; matching them does not authenticate a caller.
The only admitted workload here is generated by the trusted host, not supplied
by an untrusted agent. A production scoped-grant service remains future work.

The fixed project workflow uses one connection per boot, at most 16 requests, 32 KiB per frame, 8 KiB UTF-8 file
content/stdout/stderr, 128 KiB aggregate responses, and 16 KiB host workflow input
bound retention. Execution clears the environment, supplies an explicit PATH,
uses argv/cwd, null stdin and a separate process group. Commands have a two-second
guest deadline; the host separately stops the VM at ten seconds, with the
existing stop and runner watchdogs. The transport has three-second I/O timeouts.
A disconnected or malformed response is never replayed. An unconfirmed stop
leaves the VM unknown and blocks disk reuse. A confirmed stop after transport
failure does not establish whether a command completed.

The helper runs as guest root and can write guest files, including its own
executable, subject to Linux filesystem behavior. This is deliberately not a
path sandbox inside the VM. A command can damage the helper or evade its process
group; only the independent VM stop establishes the outer execution boundary.
No claim of adversarial isolation or production resource enforcement follows.
Knowledge placed in a VM is not confidential from an authorized reader or the
external model to which that reader sends it.

## Evidence and remaining work

On the development Mac, three consecutive real project boots passed, including
artifact receipt, exit/stderr, timeout, confirmed stops and baseline integrity.
This is functional evidence only, not M5 capacity or latency qualification.
The final source is also checked with workspace tests/lints, Linux ARM64 helper
cross-lints, and native protocol tests; those checks alone do not prove VM execution.

The fixed experiment still lacks a complete Debian toolchain, arbitrary project
manifests, streaming output and request-ID cancellation. The managed path separately
provides an authenticated socket, binary/chunked artifact transfer, reconciliation,
and executable rollback/branch operations. See the managed acceptance guide. No
concurrency or full v0.1 qualification is claimed by either path.

## Third-party provenance

The installer is pinned in `root_modules.py`. Only its BusyBox executable and
glibc loader/libc are selected; extraction never follows archive member paths.
BusyBox is GPL-2.0 and glibc LGPL-2.1-or-later; the original source remains under
its respective licenses, not Cocoon's MIT license. Source and license information:
[Debian BusyBox](https://sources.debian.org/src/busybox/),
[Debian glibc](https://sources.debian.org/src/glibc/), and
[Debian Linux](https://sources.debian.org/src/linux/).
The kernel package's pinned SHA-256 comes from the
[Debian download metadata](https://packages.debian.org/trixie/arm64/linux-image-6.12.107%2Bdeb13-arm64/download).
Build manifests record input/file/helper hashes. No third-party binaries are
committed or distributed here; publishing an image requires its own complete
license, corresponding-source and provenance packaging.
